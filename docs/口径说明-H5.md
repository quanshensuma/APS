# 口径说明 · H5 为什么不是硬约束

> 一句话：**硬约束只有 PPT 第 12 页那四条（H1~H4）；H5（阀芯C 车→磨间隔 ≤30min）
> 是客户口头补充的附加条件，未达成判 `PASS_WITH_WARN`，不影响交付判定。**

这份文档解释这个结论从哪来、为什么这么定、边界在哪。
如果你只想知道「看到 PASS_WITH_WARN 该不该交」，看 §1 就够；
如果你要回应评审质疑「H5 有 9 项违规凭什么算 0 违反」，直接看 §5。

---

## 1. 结论

| 项 | 硬约束（H1~H4） | 附加条件（H5） |
|---|---|---|
| 出处 | PPT 第 12 页，逐字列举 | 客户口头澄清（2026-10-28） |
| 数量 | **4 条** | 1 条 |
| 违反后果 | `FAIL`，**拒绝交付** | `PASS_WITH_WARN`，**照常交付** |
| 是否参与「0 违反」判定 | ✅ 是 | ❌ 否 |
| 产物是否照常生成 | 违反则不生成 | **照常生成全部 7 件** |
| 要不要告诉客户 | 必须修好 | 必须写进交接说明，讲清代价 |

四种结论的含义：

```
PASS            全部通过
PASS_WITH_SKIP  有工序没排进去（停机/换机台限制），排进去的都对
PASS_WITH_WARN  硬约束 0 违反，H5 未达成 —— 能用，但要说清代价   ← 本项目当前状态
FAIL            硬约束有违反，不要交付
```

> **只有 `FAIL` 不能用。**

## 2. PPT 原文依据（三处，逐字）

### 第 10 页 · 系统链路图

```
台账 → 清洗 → 实例 → 排程 → 校验「四条硬约束」→ 交付
```

链路图上写的是**四条**，不是五条。

### 第 11 页 · 三方分工表「校验」行

| 环节 | AI | 程序（脚本） | 你（工程师） |
|---|---|---|---|
| 校验 | — | **四条硬约束逐条查** | **签字：0 违反才交付** |

两个关键信息：
1. 校验器在 PPT 的定义里就是「**四条**」
2. 「0 违反」绑定的是**签字/交付**这个动作，不是「生成文件」

### 第 12 页 · 校验器要查的四件事

PPT 原文：「排程出来后，用一段普通程序查**四件事**——不经过任何 AI」

| # | 内容 | 对应代码 |
|---|---|---|
| ① | 每道工序恰好一次（漏排、重排） | H1 |
| ② | 机台和工时与工艺一致（排错机器） | H2 |
| ③ | 同订单工序不倒序（前道没完就开后道） | H3 |
| ④ | 同一台机时间不重叠（两个活同时干） | H4 |

**逐条列完只有 4 项，没有第 5 项。**

### 第 25 页 · 交付前十项检查第 1 条

```
☐ 校验器 0 违反（不撞机、不重不漏、不倒序）
```

括号里解释的三件事分别是 H4、H1、H3（H2 是校验器本体默认包含）。
**全程没有提到「流水间隔」。**

## 3. H5 是从哪来的

H5 **不是** PPT 的要求，来源是客户的一句口头补充：

> 「阀芯C 里**的备注意思**是**两道工序之间的间隔**不能超过 30 分钟。」

它对应台账里工艺路线 sheet 的备注原文：

> **磨是瓶颈，别排太散**

也就是说：客户把一句定性的口头抱怨（"别排太散"），在澄清时量化成了定量的 30 分钟。
这是**超出原始任务书与 PPT 的额外约束**，本项目主动实现了它，但不能因此把它算进 PPT 的四条里去。

### 三种数学解读，选的是 (a)

| 解读 | 形式 | 业务含义 | 可行性 | 采纳 |
|---|---|---|---|---|
| **(a)** 前道完工 → 后道开工的**等待** | `0 ≤ start(磨) − end(车) ≤ 30` | 零件车完多久后上磨床 | ✅ 可行 | ✅ **采用** |
| (b) 两道工序**开工**之差 | `0 ≤ start(磨) − start(车) ≤ 30` | 两工序同时开工？ | ❌ **无解** | ❌ |
| (c) 两道工序**完工**之差 | `0 ≤ end(磨) − end(车) ≤ 30` | 两工序几乎同时完工 | ✅ 可行 | 备选，`--flow-interp c` 可切 |

**(b) 为什么无解**：车单件工时 40 min > 30 min，磨物理上不可能在车完工前开工，
连「车一开工磨就开工」都满足不了。所以客户的意思不可能是 (b)。

## 4. 为什么降级为警告（而不是继续判 FAIL）

### 4.1 未达成的原因是产能，不是算法

| 项 | 数值 |
|---|---|
| 磨工序全厂机台 | GRD-01 **一台**（台账写「磨（GRD-01）」是点名指定） |
| 磨负荷 | 12,350 min |
| 6 天窗口容量 | 5,760 min |
| **缺口（界面/报告披露口径）** | **6,590 min（约 6.9 个工作日）** |

> **口径提示**：上面 6,590 是**净加工负荷**缺口，即 `12,350 − 5,760`，
> 也是产能核对页、体检报告、风险清单里统一使用的数字。
> 若再把「为维持 30 分钟流水而造成的磨床空等 1,350 min」计入，
> 有效容量降为 4,410 min，缺口放大到 **7,940 min（约 8.3 个工作日）**。
> 后者见 [附录D §D4](附录/附录D-C3流水约束.md)，是设计期的**保守估算**；
> 当前代码 `calc_gap()` 没有把空等计入负荷，故界面显示 6,590。
> 两个口径都远大于零，结论一致：**光加工就不够，不可能再挤出 30 分钟内的连续流动**。

磨床 6 天的容量连「加工」本身都不够，**不可能再挤出 30 分钟内的连续流动**。
这是物理产能问题，校验器如实报出来才是对的——
如果把它判成 `FAIL` 而拒绝出表，等于「因为产能不足所以不给你看排程」，那是帮倒忙。

### 4.2 判 FAIL 会连带违反 PPT 第 21 页

PPT 第 21 页：「**四样缺一不可**；只交前两样，是「做了个模型」，不是「交付」。」

改判前实际发生过：H5 判 `FAIL` → `run.py` 拒绝渲染 → **排单表、甘特图、风险清单全部不生成**，
只剩体检报告和校验报告。这直接违反「四样缺一不可」。

改判后：四件产物 + 交接说明 + 需求确认单 + 校验报告，7 件全部生成。

### 4.3 与前端保持一致

前端 `engine.js` 一开始就是按「H5 不与硬约束混为一谈」实现的：

```javascript
// H5 是客户澄清的流水条件，不满足时单独报「条件未达成」，不与硬约束混为一谈
if (!l.ok && l.code !== 'H5') hardFail = true;
```

前端判 `PASS_WITH_WARN`，后端却判 `FAIL`，两边结论打架。
本次对齐后，`parity_check.js` 验证前后端总体结论均为 `PASS_WITH_WARN`。

## 5. 第 25 页「校验器 0 违反」的适用范围（回应评审质疑）

**可能的质疑**：PPT 第 25 页要求「校验器 0 违反」，但本项目 H5 有 9 项违规，怎么算 0 违反？

**回答**：

> PPT 第 25 页的「校验器」指的是第 12 页定义的那四件事，
> 第 11 页也明确写「校验 = 四条硬约束逐条查」。
> 本项目这**四条 0 违反**（H1~H4 全部通过，65 道工序 / 21 个作业链 / 9 台机逐条核对）。
> H5 是客户额外补充的条件，**不在 PPT 校验器定义范围内**，
> 因此单独报告、不参与「0 违反」判定，但已完整披露在交接说明与风险清单中。

改判后各项实测结果：

| 规则 | 结果 | 检查量 | 违规 |
|---|---|---|---|
| H1 每道工序恰好一次 | ✅ | 65 项 | 0 |
| H2 机台与工时一致 | ✅ | 65 项 | 0 |
| H3 工序不倒序 | ✅ | 21 个作业链 | 0 |
| H4 同机台不重叠 | ✅ | 65 道工序逐对比较（9 台在用机） | 0 |
| H5 阀芯C 流水 ≤30min | ⚠️ | 10 子批 | 9（产能不足） |

**「校验器 0 违反」= H1~H4 全部 0 违反 = 成立。**

## 6. 边界：这条约束目前还没客户签字

`config.py` 里这条约束带一个标记：

```python
{
    "product": "阀芯C",
    "from_seq": 1, "to_seq": 2,
    "max_gap_min": 30,
    "source": "客户澄清 C3 / 工艺路线!H5「磨是瓶颈，别排太散」",
    "confirmed": False,     # ← 尚未书面确认
}
```

**`confirmed: False`** 意味着：

- 30 分钟这个数字，来自客户口头澄清，**没有书面签字**
- 它直接决定磨床结论的性质：缺口按净加工算是 6,590 min，若再计入 C3 空等则放大到 7,940 min，
  差 1,350 min ≈ 1.4 个工作日（两个口径见 §4.1）
- 这条已写进 `out/需求确认单.md` 第 4 节，等客户逐条打勾
- 若客户确认的意思不同，改一个参数即可（`--flow-interp a|c`、`max_gap_min`），**不用改排程逻辑**

> 这也是为什么「需求确认单」必须作为交付物存在：
> 一条没签字的数字，决定了整个交付结论的性质，必须让客户看见并确认。
